## Overview

`mrpt_path_planning` (C++17, namespace `mpp`, BSD-3) plans kinematically
feasible paths on planar environments with point-cloud obstacles. It uses
MRPT's **Parameterized Trajectory Generators (PTGs)** as motion primitives, for
vehicles of arbitrary shape (differential-drive, Ackermann, holonomic).
Dependencies: MRPT 3.x colcon modules.

## Repository layout

Three colcon/ROS 2 packages, each with its own `package.xml` and
`CMakeLists.txt`. There is no top-level CMake build.

```
mrpt_path_planning_core/        Headless library. CMake package and target:
│                               find_package(mrpt_path_planning) / mpp::mrpt_path_planning
├── include/mpp/algos/          Planners (TPS_Astar, TPS_Astar_Bidir), cost evaluators,
│                               NavEngine, TrajectoryFollower, collision/interpolation
│                               helpers, 3D scene and SVG rendering (no windowing)
├── include/mpp/data/           Planner I/O, SE(2) states, motion tree, trajectories
├── include/mpp/interfaces/     Obstacle sources, vehicle interfaces
├── include/mpp/ptgs/           PTG implementations (DiffDrive_C, HolonomicBlend)
├── src/                        Implementations; registerClasses.cpp registers RTTI classes
├── tests/                      GTest suite
├── doc/                        Doxygen/Sphinx sources
└── wip-experimental/           TPS_RRTstar, not built
mrpt_path_planning_apps/        Needs mrpt_gui, cli11, mvsim (optional)
├── path-planner-cli/           Planning CLI (3D viz window, or --no-gui)
├── mrpt_path_planning_viz/     Private 3D visualization helpers for the apps
```

Consumers that only need the algorithms should depend on
`mrpt_path_planning_core`, which avoids pulling in `mrpt_gui`.

## Conventions

- Public headers under `include/mpp/{algos,data,interfaces,ptgs}/`, included as
  `<mpp/...>`. Each source file starts with the project license banner.
- Classes created by name from config files (planners, cost evaluators, PTGs)
  use MRPT RTTI and must be registered in `src/registerClasses.cpp`.
- Planner parameters are exposed as YAML (`params_as_yaml()` /
  `params_from_yaml()`); PTGs are configured from INI sections.
- No one-line `if` bodies, one variable per declaration, anonymous namespaces
  instead of `static` for file-local symbols.

## Core concepts

**PTGs.** A PTG is a family of trajectories indexed by `k` (or angle `alpha`),
traveled distance `d` and, for speed-trimmable PTGs, a speed scale in `[0,1]`.
It maps `(k, step)` to pose and twist, and workspace points back to TP-Space
(`inverseMap_WS2TP`). `DiffDrive_C` generates circular arcs (with `K=-1` for
reverse motion); `HolonomicBlend` generates holonomic motions with velocity
ramps defined by runtime-compiled expressions.

**TP-Space collision checking.** Obstacles in the robot frame are projected
into TP-Space: for each trajectory `k`, the free distance before collision.
`DiffDriveCollisionGridBased` precomputes a collision grid that `TPS_Astar`
queries in a single batched pass per expanded node (`updateTPObstacles()`);
`tp_obstacles_single_path()` is the per-trajectory variant.

**Lattice A\* (`TPS_Astar`).** SE(2) is discretized into cells of
`grid_resolution_xy` x `grid_resolution_yaw`. Neighbors are not fixed grid
adjacencies: they are generated by forward-simulating PTG trajectories from the
node, sampling a subset of `k` (plus the direct-to-goal direction), several
time horizons (`ptg_sample_timestamps`) and, optionally, speeds. The planner
keeps the best edge per target cell and rewires the motion tree when a cheaper
parent is found.

**Heuristics.** SE(2) goals use the Lie-group distance, R(2) goals the
Euclidean distance; both add a heading-alignment term and are divided by the
maximum PTG speed so they are in time units. Optional: Reeds-Shepp distance
(`use_reeds_shepp_heuristic`, requires all PTGs to be `DiffDrive_C`), and
weighted A\* via `heuristic_epsilon` (default 1.0, i.e. exact A\*).

**Reeds-Shepp shot** (`use_reeds_shepp_expansion`, pose goals). Near the goal,
the shortest Reeds-Shepp path is executed as a chain of forward/reverse C-PTG
edges, each collision-checked; a clear chain becomes a goal candidate.

**Cost model.** Edge cost = PTG segment estimated execution time + the sum of
cost evaluators: `CostEvaluatorCostMap` (obstacle-proximity penalty) and
`CostEvaluatorPreferredWaypoint` (reward near given waypoints).

**Bidirectional A\* (`TPS_Astar_Bidir`).** Searches forward from the start and
backward from the goal (predecessors from inverted PTG relative poses) until
both settle the same lattice cell, then stitches and refines the path. C-PTGs
only; the core always runs exact A\*.

**Post-processing.** `refine_trajectory()` re-fits PTG parameters so edges
connect the exact node poses; `plan_to_trajectory()` samples the path in time.

**Navigation.** `NavEngine` is a state machine for waypoint-sequence navigation
with a planner thread, enqueued motion commands and `VehicleMotionInterface`.
`TrajectoryFollower` is a ROS-free pure-pursuit core with predictive safety
(footprint sweep against live obstacles), consuming a `Trajectory` and emitting
`SampledTrajectory` chunks via `TrajectoryVehicleInterface`.

## TPS_Astar::plan() flow

```
1. Create root node at the start pose; push it to the open set.
2. While the open set is not empty and not timed out:
   a. Pop the node with the lowest f = g + eps*h.
   b. If it is in the goal cell (or a Reeds-Shepp shot reaches the goal): done.
   c. Transform and square-clip obstacles to the node's local frame.
   d. For each PTG: update its dynamic state, sample (k, time, speed) triples,
      compute free distances, keep the best collision-free edge per cell.
   e. For each neighbor: edge cost = exec time + cost evaluators; if it improves
      g, update the node, the open set and the motion tree (rewiring).
3. Return success, costs, and the motion tree (best node even on failure).
```

## Invariants

- **Exact poses.** Nodes are indexed by lattice cell but store exact SE(2)
  poses, so discretization error does not accumulate along the path.
- **Conservative collision grids.** A grid cell stores the distance of sample
  `n` if any point of the cell is within `r_n + clearance` of the footprint,
  with `r_n` bounding footprint motion until the next sample. Free distances are
  therefore certified lower bounds for the continuous motion.
  `tests/test_collision_grid_soundness.cpp` checks this by brute force, and the
  batched query must stay identical to the per-point one.
- **Clipping matches grid reach.** Local obstacles are clipped to
  `obstacle_clipping_distance()`, the same reach the collision grid covers
  (`refDistance + robotRadius + clearance`).
- **Goal semantics.** R(2) goals match position only (`sameLocation()`); SE(2)
  goals match all three coordinates.
- **Admissibility.** With `heuristic_epsilon = 1`, heuristics must stay
  admissible and consistent (`tests/test_heuristic.cpp`,
  `tests/test_reeds_shepp.cpp`).

## Known limitations

- Obstacles are static during a plan (no time-dependent obstacles).
- Trajectory indices are sampled uniformly plus the direct-to-goal direction;
  maneuvers through narrow gaps may be missed.
- No global path smoothing or shortcutting beyond `refine_trajectory()`.
- `TPS_RRTstar` in `wip-experimental/` is not maintained or built.
